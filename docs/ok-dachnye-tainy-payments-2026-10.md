## 1. Главный вывод

Прежняя гипотеза «в ОК платежи через VK Bridge невозможны» **ослаблена**.
Официальная документация VK Mini Apps (раздел «Платежи виртуальной валютой»)
описывает продажу виртуальных ценностей **в Одноклассниках именно через
`VKWebAppShowOrderBox`**, но с **другой серверной схемой, чем во ВКонтакте**.
Наш платёжный Worker этой схемы не реализует. Это конкретный дефект кода,
который объясняет «Платежи не работают» и не требует предположения, что метод
в ОК не поддерживается. **Не доказано** — подтверждается только пробным
платежом в тестовом режиме на настоящем ОК (§5).

Косвенный довод в ту же сторону: в таблице apiok.ru/apps/vk строка
`VKWebAppShowOrderBox` есть не во всех версиях страницы (у Codex её нет) —
страница, возможно, меняется; документация VK при этом прямо показывает вызов.

## 3. Что в нашем Worker не совпадает с документацией ОК

Файл `services/payments/src/index.ts` (протокол VK):

| # | Расхождение | Следствие |
|---|-------------|-----------|
| 1 | `fetch` отвечает **405 на любой не-POST** запрос. Подтверждение покупки от ОК — **GET**. | Если ОК-адрес указывает на этот Worker, подтверждение покупки отклоняется, ОКи не переводятся, покупка не завершается — похоже ровно на «платежи не работают». |
| 2 | Нет разбора GET-параметров `callbacks.payment` и ответа `true`; нет ответа с `Invocation-error` для ошибок ОК (`1001`, `104`). | Нужен отдельный маршрут. |
| 3 | `get_item` возвращает цену **20 «голосов»** без учёта `site=OK`; ОК ждёт цену **в ОКах**. | В окне покупки в ОК показалась бы неверная сумма; курс голос↔ОК **неизвестен**. |
| 4 | Подпись GET считается по **другому набору** параметров и, возможно, **другим ключом** (`VK_APP_SECRET` — «защищённый ключ» ВК-приложения). Какой секрет подписывает ОК-callback у приложения, созданного через VK Mini Apps, документация не уточняет. | Выяснить пробным платежом/поддержкой, не гадать. |
| 5 | Нет проверки `amount` на соответствие каталогу (в ОКах) и `product_code`. | Обязательное требование ОК. |
| 6 | Игра везде пишет «20 голосов»; в ОК единица — ОКи. | Текст цены для `vk_client=ok` нужно менять (требование модерации VK: цена видна до «Купить» — оно относится и сюда). |
| 7 | У `get_item` нет `expiration`, значит платформа не кеширует. Если добавить кеш, он **раздельный по языку, но не по площадке** — цены ВК и ОК нельзя будет возвращать одним кешем. | Не включать кеширование без проверки `site`. |

## 4. SDK: документированный способ подключения к связанному приложению

Для текущей схемы (п. 1 §2) **SDK ОК не нужен**: покупка запускается через VK
Bridge. FAPI понадобился бы только для классического пути. Документированная
цепочка: подключить `//api.ok.ru/js/fapi5.js`; взять параметры запуска
`FAPI.Util.getRequestParameters()`; вызвать `FAPI.init(api_server,
apiconnection, onSuccess, onError)` до любых других методов; документация
перечисляет параметры, которые нужно передавать после переходов внутри iframe:
`api_server`, `apiconnection`, `web_server`, `application_key`, `session_key`,
`session_secret_key`.

Что **не** считаем выводом: отсутствие этих параметров в адресе запуска или
отсутствие глобального `FAPI` само по себе ничего не доказывает — SDK
подключается скриптом, а параметры может передавать оболочка иначе. Годится
только положительный результат: успешный `FAPI.init` на живом ОК. Если путь
через Bridge заработает, этот эксперимент не нужен.

## 6. Повторные уведомления и идемпотентность

Требование: повторный callback **не должен** повторно выдать покупку.

| Вопрос | Оценка |
|--------|--------|
| Что делает наш сервер при повторе? | Ничего не выдаёт: Worker **stateless**, только подтверждает. Для ВК повторный `order_status_change` по тому же `order_id` возвращает тот же ответ — как просит документация. Для ОК такой логики пока нет (§3.1–2). |
| Может ли повтор задвоить выдачу? | **Нет по конструкции**: оба товара — одноразовые флаги (`noAds`, `unlimitedHints`), их выдаёт клиент по успешному результату `ShowOrderBox`, повторная установка флага ничего не меняет. Расходуемых товаров (валюта) в каталоге нет. |
| Что делает ОК при повторах? | Вызывает callback до 3 раз с паузой 5 с, пока нет успешного ответа; затем отменяет транзакцию и возвращает деньги. Значит, **ответ `true` на уже обработанный `transaction_id` обязателен** (иначе ОК ложно отменит оплаченную покупку). |
| Слабые места | (а) нет журнала `transaction_id`: сервер не отличает «первое подтверждение» от «повтора» — для текущих флагов безвредно, для будущей валюты — нет; (б) выдача **только на клиенте**: если клиент закрыт до результата, а ОКи списаны, у игрока нет товара и нет способа «восстановить покупку» (серверного учёта нет); (в) клиентский результат не подписан — как и сейчас во ВК. |
| Как сделать безопасно, если реализовывать | Идемпотентный ответ `true` для повторного `transaction_id` (хранить id в Cloudflare KV/D1 или считать повтор безопасным, пока SKU — флаги); проверка `amount`/`product_code`/`sig`; при расходуемых товарах — серверный ledger; при желании — восстановление покупок по `uid`. Это **предложение**, не реализовано. |

## 7. Влияние на уже принятое решение

Отключение платежей в ОК (`caps.payments=false` при `vk_client=ok`) оставлено как
**временная мера** и даёт правильное поведение до реализации: магазин в ОК не
показывается. Но по §1 она, вероятно, скрывает путь, который можно сделать
рабочим. **Рекомендация (для решения Codex/владельца):** не снимать отключение,
пока не выполнено: (1) осмотр §5; (2) серверная часть по §3; (3) успешный
тестовый платёж в ОК (тестовый режим не списывает ОКи); (4) решение владельца
о публикации. Реальные платежи — только отдельным разрешением.

## 10. Подготовленная реализация (локально, без развёртывания) — 7 октября

Поправка Codex принята: потеря покупки при закрытии игры после списания — дефект
даже для одноразового флага, восстановление входит в реализацию.

Сделано в `services/payments` (коммит локальный, не развёрнуто, магазин ОК выключен):

- `GET /ok` — `callbacks.payment`: подпись, товар, сумма по `priceOk`, учёт
  транзакции, ответ `true`; повтор той же `transaction_id` — снова `true` без второй
  записи; тот же `transaction_id` для другой покупки — ошибка; сбой записи —
  ошибка (ОК повторит/вернёт деньги), а не `true`.
- `POST /` с `site=OK` (`get_item`) — отдаёт `priceOk`; без неё — ошибка, голоса вместо ОКов не подставляются.
- `GET /ok/restore` — подписанные параметры запуска (`sign`, HMAC-SHA256 по
  `vk_*`, формат по странице «Подпись параметров запуска») → список купленных SKU пользователя.
- Учёт — Cloudflare KV с ключами по покупке (`ok:p:{uid}:{sku}`, `ok:tx:{id}`): независимые
  записи без «читать-изменить-записать», потери при параллельных покупках нет.
- Путь ВК не изменён (ВК-ветка `order_status_change` по-прежнему stateless).

**Не угадывали, нужно от владельца/проверки:**
1. Цены в ОКах (`priceOk`) — пока не заданы; без них `/ok` и `get_item` для ОК отказывают.
2. Секрет подписи GET-уведомления ОК — `OK_APP_SECRET`; какое поле кабинета, неизвестно.
3. Равенство `uid` из уведомления ОК и `vk_user_id` запуска в ОК — на нём держится
   восстановление; при неравенстве вернёт пусто (безопасно), но не восстановит.
4. Подписывает ли запуск в ОК тем же «Защищённым ключом», что и ВК.
5. HTTP-статус ответа при ошибке (отдаём 200 + заголовок `Invocation-error`) и
   нужна ли подписка на `method`; тела `true` без обёртки.
6. KV-пространство `PURCHASES` (создаёт владелец командой из `wrangler.toml`).

**Не сделано в этом заходе:** клиентская часть (кнопка в ОК, цены в ОКах в тексте,
вызов `/ok/restore` при запуске и применение результата), включение `caps.payments`
в ОК, развёртывание, платёж в тестовом режиме.

**Проверки:** 37 новых тестов + 14 прежних (`services/payments`); негативные
контроли — четыре мутации (без проверки суммы, повторная запись, восстановление
без `vk_client=ok`, `true` при сбое хранилища) каждая роняет ровно один тест;
независимо посчитанные подписи MD5 и HMAC в тестах. Настоящий формат подтвердит
только тестовый платёж на живом ОК.

> **§10 устарел в части хранилища:** KV-учёт двумя записями заменён журналом на
> Durable Object (§11). Неатомарная запись больше не считается подтверждением.

## 11. Надёжная схема подтверждения и восстановления (ОК и ВК) — ред. 7 октября

**Источник правды о покупке — серверный журнал**, а не ответ платёжного окна в
клиенте. Покупка считается совершённой, только если журнал её записал.

**Журнал.** Durable Object `LedgerDO`, один объект на
`приложение : площадка : режим : пользователь`. Операции одного объекта
выполняются по очереди; запись транзакции (`tx:<id>`) и покупки (`p:<sku>`) идёт
**одной транзакцией хранилища** — либо обе, либо ни одной. KV не используется: он
eventually consistent и не умеет атомарно менять два ключа.

**Подтверждение (ОК — GET `/ok`; ВК — `order_status_change`):**
1. настройки и подпись (иначе ошибка, не подтверждение);
2. принадлежность приложению: `application_key` ОК совпадает с настроенным, SKU из
   каталога **этого** приложения;
3. **поиск транзакции в журнале раньше проверки цены**: повтор уже принятой
   транзакции подтверждается тем же ответом, даже если цена с тех пор изменилась;
   тот же номер с другим товаром/суммой — ошибка;
4. новая транзакция — сумма по текущему каталогу (ВК — голоса, ОК — `priceOk`);
5. атомарная запись; **ответ «подтверждено» — только после успешной записи**. При
   сбое — ошибка: ОК повторит запрос или отменит платёж и вернёт ОКи; ВК — тоже
   ошибка (некритичная), платёж не подтверждается.

**Режимы.** test и live — разные журналы. ВК: режим из типа уведомления
(`_test` — документированный признак). ОК: признак теста в GET не документирован,
поэтому режим задаётся деплою (`PAYMENTS_MODE`). Восстановление отдаёт только журнал
режима деплоя: в рабочем деплое тестовые покупки не выдаются.

**Изоляция приложений.** Ключ приложения входит в имя объекта журнала; SKU чужого
приложения не продаётся и не восстанавливается; восстановление сверяет `vk_app_id`.

**Восстановление (клиент — ещё не сделано).** При запуске и после каждой покупки
игра отправляет свои подписанные параметры запуска на `/vk/restore` или
`/ok/restore` и применяет полученные SKU. Ответ платёжного окна клиент использует
лишь для мгновенного отклика, затем сверяется с журналом. **Объединение, а не
замена:** покупки ВК, сделанные до включения журнала, в журнале отсутствуют —
локальные флаги не сбрасываются.

**ВК без журнала.** Пока привязка `LEDGER` не развёрнута, ВК подтверждает заказы
как раньше (рабочий путь не ломается), но без учёта и без восстановления.

**Проверки:** 53 теста в `services/payments`; поддельное хранилище с настоящей
семантикой отката транзакции. Негативные контроли (каждая мутация роняет тесты):
цена до поиска транзакции (1), один журнал для test и live (3), SKU без проверки
приложения (2), без проверки `application_key` (1), проглоченный сбой записи (3).

**Остаются неподтверждёнными:** секрет подписи ОК; признак тестового режима в GET
ОК; что `uid` в уведомлении ОК равен `vk_user_id` при запуске в ОК; формат ошибки ОК
(HTTP 200 + `Invocation-error`); цены в ОКах; приходит ли `site=OK` при версии API 5.131.

## 12. Тестовый запуск «Дачных тайн» в ОК без изменения боевого адреса

**Что подтверждено документацией** (dev.vk.com, прочитано 07.10.2026):
- «Размещение»: настройки платформ «Мобильное приложение», «Десктопная версия сайта»,
  «Мобильная версия сайта» действуют для запуска **из ВКонтакте и Одноклассников**;
  у каждой есть «URL» и «Режим разработки» — адрес, который платформа загружает
  **администраторам** вместо «URL»; остальным пользователям подмены нет.
- «Другие площадки»: пока ОК-модерация не пройдена, в ОК приложение запускает только
  создатель; ссылка запуска в ОК — `https://ok.ru/app/vk_app54767366`.
- «Тестовые группы»: только пользователи ВКонтакте — для ОК не подходят.
- «Тестирование платежей»: для операций с ОКами тестировщик должен быть администратором
  с правом «Тестирование» (или создателем), связать VK ID и OK ID и получить права
  разработчика в ОК; список — «Платежи → Подключение → Тестировщики платежей».

**Чего документация не говорит:** применяется ли URL «Режима разработки» при
запуске **в Одноклассниках**. Описание приоритетов URL говорит о «запуске
мини-приложения администраторами» без указания площадки.

**Вывод:** подтверждённого способа нет; кандидат — «Режим разработки» десктопной
версии, но включать его, не зная, действует ли он в ОК, нельзя (он касается также
администраторов во ВК; боевой «URL» при этом не меняется).
