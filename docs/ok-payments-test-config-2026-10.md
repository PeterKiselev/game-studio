# «Дачные тайны» в ОК: подготовка тестовой покупки — проверка обработчика и оставшаяся конфигурация

Дата: 14 октября 2026. **Только проверка и список.** Обработчик не развёрнут, сборка с магазином ОК
не сделана, кабинет не менялся, покупок не было. Секреты в документе не приводятся.

Исходное: живой запуск в ОК подтверждён — маркер `5a83e6b`, `клиент: ok`, платформа
`desktop_web_ok`; режим разработки после проверки выключен.

## 1. Проверка подготовленного обработчика (`services/payments`)

- Юнит-тесты: **61/61** (`npx vitest run` в `services/payments`); интеграционные с настоящим Durable
  Object в локальном workerd: **10/10** (`npm run test:int`). Облако не используется.
- `GET /ok` (`callbacks.payment`): настройки → подпись → `application_key` → метод → не подписка →
  `uid`/`transaction_id`/`amount` → SKU этого приложения → **сначала поиск транзакции** (повтор —
  `true`, тот же номер с другим товаром/суммой — ошибка) → сумма = `priceOk` → атомарная запись →
  только потом `true`. Сбой записи — ошибка (ОК повторит или вернёт ОКи).
- Рабочий режим ОК **заблокирован в коде**: при `PAYMENTS_MODE` ≠ `test` маршруты ОК отвечают ошибкой.
- `POST /` `get_item` c `site=OK` отдаёт цену в ОКах (`priceOk`); без неё — ошибка, голоса не
  подставляются.
- `GET /ok/restore`: подписанные параметры запуска (`sign`, ключ — `VK_APP_SECRET`) → купленные SKU.
- Изолированный тестовый деплой описан в `wrangler.toml`: `[env.oktest]`, имя
  `dachnye-tainy-payments-oktest`, `PAYMENTS_MODE = "test"`, журнал `LEDGER` (Durable Object).

Код соответствует прочитанной документации ОК; **подтвердит его только тестовая покупка** на живом ОК.

## 2. ⚠ Нужно решение до реализации: `get_item` для ОК идёт на адрес ВКонтакте

По документации («Продажа виртуальных ценностей в Одноклассниках») покупка в ОК — это
`VKWebAppShowOrderBox`; запрос цены `get_item` с `site=OK` приходит **POST на «URL для платёжных
уведомлений ВКонтакте»**, а GET-подтверждение — на «URL для … Одноклассников».

В кабинете «URL для ВКонтакте» — **боевой** Worker `dachnye-tainy-payments.<…>.workers.dev`.
Значит, тестовый сервер `oktest` один покупку в ОК не проведёт: цену в ОКах должен отдать боевой
Worker. Какой код на нём сейчас развёрнут, в репозитории не записано — вероятно, ранняя версия,
которая на `site=OK` отвечает ценой **в голосах** (это, возможно, и было «платежи не работают»).

| Вариант | Что затрагивает | Оценка |
|---|---|---|
| **А. Обновить боевой Worker** версией, где для ВК всё как сейчас (без журнала, `LEDGER` не привязан), а `get_item` с `site=OK` отдаёт `priceOk` | Боевой деплой (код), без правок кабинета | **Рекомендую.** Сначала выяснить, что развёрнуто сейчас (`npx wrangler deployments list` — владелец), сравнить с репозиторием; тестами подтвердить, что ответы ВК не меняются. Цена в ОКах для товара появится и для обычных игроков ОК — но магазин в ОК в боевой сборке скрыт, поэтому продать там ничего нельзя. |
| Б. На время теста направить «URL для ВКонтакте» на `oktest` | Кабинет: боевые покупки ВК на время теста идут на тестовый сервер | Не рекомендую: затрагивает реальные платежи ВК; нужен ещё `VK_APP_SECRET` на `oktest`, а риск ошибки — у живых игроков. |

## 4. Что подтвердит только тестовая покупка

Какой ключ подписывает GET ОК; равен ли `uid` уведомления `vk_user_id` запуска в ОК (на нём держится
восстановление); есть ли признак тестового режима в GET; формат ошибки (200 + `Invocation-error`);
приходит ли `site=OK` в `get_item` при API 5.131.
