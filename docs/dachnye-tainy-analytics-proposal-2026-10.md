# «Дачные тайны» — минимальная аналитика: предложение до реализации

Дата: 14 октября 2026. **Только предложение.** Ничего не отправляется, облако не подключается,
расходов нет, политика не публикуется — до ревью Codex и решения владельца.

## 1. Что хотим узнать (и ничего сверх этого)

| Вопрос | Событие |
|---|---|
| Сколько игроков начинают и заканчивают каждое дело | `case_start`, `case_complete` |
| Переходят ли к следующему делу главы сразу после развязки | `next_case` |
| Открывают ли дело дня — сегодняшнее или прошлое | `daily_open` |
| Возвращаются ли в другой день (D1, D7) | `session_start` с днями, посчитанными на устройстве |

## 2. Что уже есть в коде

`packages/game-kit/src/analytics.ts` пишет события только в консоль и в память вкладки — ничего
не сохраняется и не отправляется. События `case_start`, `case_complete`, `next_case` уже вызываются;
`daily_open` и дни возврата — новые.

**Найдено при разборе:** `case_mistake` передаёт `key` — ключ клетки, то есть ответ игрока. Пока это
только консоль, но в отправку такое попадать не должно: при реализации поле убирается, а в отправку
идут только события из белого списка ниже.

## 3. Состав данных — белый список

Только эти события и только эти поля. Всё остальное, что вызывает `app.track`, остаётся
отладочным и никуда не уходит.

| Событие | Поля | Значения |
|---|---|---|
| `session_start` | `days_since_first`, `days_since_last`, `first_day`, `platform`, `build` | дни по московской дате: 0, 1, 2…; `first_day` — московская дата первого запуска на этом устройстве (YYYY-MM-DD); `platform` — web/vk/ok; `build` — версия сборки |
| `case_start` | `case_id`, `kind`, `resumed` | `kind` — plot / chapter / daily; `resumed` — продолжение незаконченного |
| `case_complete` | `case_id`, `kind`, `stars`, `hints`, `duration`, `step_wrong` | `hints` — 0, 1, 2, 3+; `duration` — <2, 2–5, 5–10, 10+ мин; `step_wrong` — неверные выборы на шаге «показания/версия»: 0, 1, 2+ |
| `next_case` | `from`, `to` | id дел главы |
| `daily_open` | `case_id`, `when` | `when` — today / past; для past — сколько дней назад: 1, 2–7, 8+ |

**Не собираем:** ID и имена VK/ОК, IP-адрес, отметки и ответы в таблицах, выбранные версии,
тексты, точное время событий (только московская дата первого запуска и счётчики дней), данные
о покупках сверх того, что уже есть у платформы.

## 4. Идентификатор: два варианта, рекомендую без него

**Вариант А — постоянный случайный ID устройства** (`crypto.randomUUID()` в `localStorage`).
Это **псевдонимный** идентификатор, не анонимный: он связывает события одного устройства во
времени. Требования к нему определяет политика и правовая оценка (возможно, персональные данные
по 152-ФЗ). Минусы: два устройства — два «игрока»; очистка данных браузера — новый ID.

**Вариант Б — без постоянного ID (рекомендую для первого шага).** Возврат считает само
устройство: при запуске оно знает дату первого запуска и дату прошлого визита (по Москве) и
отправляет только `days_since_first`, `days_since_last` и `first_day`. Тогда:

- D1 для когорты дня X = число первых за день запусков с `first_day = X` и `days_since_first = 1`,
  делённое на число первых запусков (`days_since_first = 0`) с `first_day = X`;
- воронка дел — простые счётчики `case_start` / `case_complete` по `case_id`.

События одного человека при этом между собой не связываются. Ограничение варианта Б: нельзя
посмотреть путь отдельного игрока (например, «кто бросил на деле 2, вернулся ли он»). Если это
понадобится — отдельное решение о варианте А с правкой политики.

**Честная оговорка:** даже без ID набор полей (`first_day` + платформа + время получения на
сервере) в малой выборке может сузить круг до конкретного человека. Это ещё один довод сразу
агрегировать на сервере и не хранить сырые события дольше нужного.

## 5. Схема хранения

### Этап 1 — только на устройстве (можно делать после ревью, без отправки)

- Даты для возврата — в сохранении игры, новое необязательное поле
  `visits: { first: 'YYYY-MM-DD', last: 'YYYY-MM-DD' }` (версия сохранения та же).
- Очередь событий белого списка — отдельный ключ `localStorage`
  `studio:dachnye-tainy:analytics`, не в сохранении: не попадает в облачные сохранения
  платформы. Не больше 200 событий, старые вытесняются. **Никуда не отправляется.**
- Переключатель «Отправлять статистику игры» — в данных есть, в интерфейсе пока скрыт; по
  умолчанию выключено, пока не решено иное.
- Тесты: белый список (лишние поля и события не попадают в очередь), дни по Москве, ограничение
  очереди, отсутствие сетевых запросов (как в `playtest-restore` для обычной сборки).

### Этап 2 — сервер (отдельная карточка, только после решений из §7)

Свой Cloudflare Worker (уже есть для платежей) + D1. Включается только сборкой с адресом, как
восстановление покупок (`VITE_PAYMENTS_URL`).

```
events_raw(received_day TEXT, name TEXT, props TEXT)   -- хранится 90 дней, затем удаляется
daily_agg(day TEXT, name TEXT, key TEXT, count INTEGER) -- агрегаты, храним дольше
```

- `received_day` — дата получения, без времени; IP не записывается и не логируется; тела запросов
  в логи Worker не пишутся.
- Удаление по сроку — плановой задачей (cron) Worker.
- Бесплатные лимиты Workers/D1 **не проверены** — проверить до включения; расходы не допускаются
  без отдельного решения.

## 6. Изменения политики конфиденциальности — черновик

Действует для всех игр (`static/privacy.html`, адрес вбит в формы VK и Яндекса). **Публиковать
только одновременно с включением отправки**, не раньше и не позже. Пока отправки нет, текущая
политика остаётся верной: локальная очередь не покидает устройство.

Что меняется:

1. В «Коротко» и в разделе 3 убрать «не используют системы аналитики» — заменить на точное
   описание собственной статистики.
2. Новый раздел «Статистика игры» (черновик):

> В «Дачных тайнах» мы собираем статистику прохождения, чтобы понимать, какие дела слишком
> сложные или скучные и возвращаются ли игроки. Отправляются только события игры: начато и
> раскрыто ли дело (с числом подсказок и примерной длительностью), переход к следующему делу,
> открытие дела дня, а также сколько дней прошло с первого и с прошлого запуска на этом
> устройстве. Мы не отправляем идентификатор и имя профиля ВКонтакте или Одноклассников, ответы
> в головоломках и точное время игры, не сохраняем IP-адрес. Данные хранятся на сервере
> разработчика (инфраструктура Cloudflare) не дольше 90 дней, затем остаются только общие
> суммы без привязки к устройству. Отключить отправку можно в настройках игры.

   Если выбран вариант А — добавить: «…и случайный идентификатор устройства, созданный игрой.
   Он не связан с профилем, но позволяет связать события одного устройства между собой;
   удаляется вместе с данными сайта». И называть его так, а не «анонимным».

3. В «Хранение и удаление» — срок 90 дней и как отказаться.
4. Новая дата редакции.

**Правовой вопрос, который я не решаю:** нужен ли для варианта А (или даже Б) отдельный
порядок по 152-ФЗ — согласие, уведомление Роскомнадзора, локализация. Ответ определяет,
включать ли отправку по умолчанию или только после согласия.
