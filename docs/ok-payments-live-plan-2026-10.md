## 2. Что ещё НЕ подтверждено

| Что | Почему не доказано тестом |
|---|---|
| Восстановление именно **из серверного журнала** | «Куплено» после обновления и в другом браузере объясняется и облачным сохранением VK (`VKWebAppStorage` хранит `purchases` вместе с прогрессом). Нужен проверяемый признак того, что права пришли из `/ok/restore` (§4). |
| `uid` уведомления ОК = `vk_user_id` запуска в ОК | Восстановление ищет покупки по `vk_user_id`; если идентификаторы разные, журнал вернёт пусто (безопасно, но не восстановит). Проверяется тем же признаком (§4). |
| Признак тестового режима в GET ОК | Не документирован; в тесте режим задавал деплой. Без признака рабочий сервер не отличит покупки тестировщиков от настоящих (§3). |
| Боевые платежи | Не проводились: рабочий режим ОК заблокирован в коде; модерация ОК не пройдена. |

## 3. Разделение тестовых и настоящих покупок

Документация: тестовый режим — до модерации; после модерации платежи становятся рабочими, **но у
тестировщиков из списка «Тестировщики платежей» остаются тестовыми**. В GET ОК признака теста нет
(по документации), значит рабочий сервер должен решать сам.

**Предложение — тестовость по списку тестировщиков.** Новая настройка рабочего сервера
`OK_TEST_UIDS` (OK-uid тестировщиков, сейчас — только владелец). Уведомление от uid из списка →
журнал `test`; от остальных → журнал `live`. Это ровно правило площадки: у тестировщиков платежи
тестовые, у остальных — настоящие.
- Журналы `test` и `live` уже разные (режим входит в ключ объекта журнала).
- Восстановление отдаёт: тестировщику — `test`, остальным — `live`. Тестовые покупки владельца не
  превращаются в настоящие и не попадают в восстановление обычных игроков.
- Если в журнале кабинета или в запросах ОК найдётся документированный признак теста — заменить им
  список (проверить в «Платежи → Подключение → Логи» и по именам параметров при следующем тесте,
  без значений подписи).
- Риск: тестировщик, убранный из списка в кабинете, но оставшийся в `OK_TEST_UIDS`, — его настоящая
  покупка ушла бы в `test`. Правило: менять оба списка вместе; при сомнении — убрать из
  `OK_TEST_UIDS` (настоящий платёж важнее).

## 4. Проверка серверного восстановления без удаления прогресса

Нельзя проверять, стирая сохранение игрока. Предлагаемый способ — **проверочный режим тестовой
сборки** (флаг сборки, в боевых сборках его нет):
- при запуске игра, как обычно, запрашивает `/ok/restore`, но **дополнительно показывает в полосе
  маркера**, что вернул журнал: `журнал: no_ads, hints` / `журнал: пусто` / `журнал: ошибка 403`;
- сохранение не меняется сверх обычного (права только добавляются, как сейчас).

Сценарии:
1. Создатель после покупок → полоса «журнал: no_ads, hints». Это доказывает и восстановление из
   журнала, и равенство `uid` ↔ `vk_user_id`.
2. Другой браузер, без локальных данных → та же полоса до загрузки облачного сохранения.
3. Второй аккаунт-тестировщик без покупок → «журнал: пусто» (журнал не выдаёт чужие покупки).
4. Сервер недоступен → «журнал: ошибка …», купленное в сохранении остаётся «Куплено».

Дополнительно, без изменения кода: DevTools → Network → запрос `…/ok/restore` → ответ
`{"skus":[…]}` (параметры запуска в адресе запроса не копировать — там подпись).

## 5. Архитектура рабочего режима: путь VK не трогаем

| Адрес | Сейчас | После перехода |
|---|---|---|
| URL уведомлений ВКонтакте | боевой Worker (код 22 сентября, без журнала) | тот же Worker + **только** правка `get_item` для `site=OK` (ветка `payments-prod-okprice`, снимок ответов VK побайтно) |
| URL уведомлений Одноклассников | `oktest` (тест) | **отдельный рабочий Worker ОК** (`dachnye-tainy-payments-ok`): журнал `LEDGER`, `PAYMENTS_MODE=live`, `OK_TEST_UIDS`; маршруты `/ok` и `/ok/restore` |

Почему отдельный Worker ОК, а не журнал в боевом: код основной ветки на пути VK строже версии
22 сентября (например, новый заказ без `item_price` отклоняется) — перенос его на боевой адрес VK
изменил бы VK-платежи. Отдельный Worker ОК не касается VK вовсе; VK получает только проверенную
снимком правку `get_item`.

Изменения кода (будущий этап, после ревью этого плана):
- снять блокировку рабочего режима ОК **только** вместе с `OK_TEST_UIDS` (без списка — по-прежнему
  ошибка);
- тесты: тестировщик → `test`, остальные → `live`; восстановление по режиму; блокировка без списка;
- клиент: боевая сборка с `okPayments` и адресом рабочего Worker ОК — **только** для запуска в ОК;
  во ВКонтакте магазин и восстановление прежние.
