## 3. Разделение тестовых и настоящих покупок

Документация: тестовый режим — до модерации; после модерации платежи становятся рабочими, **но у
тестировщиков из списка «Тестировщики платежей» остаются тестовыми**. Признака теста в GET ОК
документация не описывает — но отсутствие в документации не доказывает отсутствия в настоящем
уведомлении.

**Шаг 1 — проверить настоящее уведомление.** При следующей тестовой покупке записать **имена**
параметров GET-уведомления ОК (и значение `method`), без `sig` и без идентификаторов: логирование
только имён — небольшая правка `oktest`, отдельно согласовать. Если признак теста там есть и он
документирован площадкой или подтверждён поддержкой — разделять по нему.

**Шаг 2 — если признака нет: список тестировщиков как запасной вариант.** Настройка рабочего
сервера `OK_TEST_UIDS` (OK-uid тестировщиков). Уведомление от uid из списка → журнал `test`, от
остальных → `live`.

**Это не гарантированное разделение, а ручная копия списка площадки.** Площадка решает, тестовый ли
платёж, по своему списку «Тестировщики платежей»; наш `OK_TEST_UIDS` — копия, которую ведут руками,
и она может разойтись с оригиналом.
- Журналы `test` и `live` уже разные (режим входит в ключ объекта журнала).
- Восстановление отдаёт: тестировщику — `test`, остальным — `live`. Тестовые покупки владельца не
  превращаются в настоящие и не попадают в восстановление обычных игроков.
- Если в журнале кабинета или в запросах ОК найдётся документированный признак теста — заменить им
  список (проверить в «Платежи → Подключение → Логи» и по именам параметров при следующем тесте,
  без значений подписи).
- **При расхождении нельзя автоматически предпочитать `live`** (и `test` тоже): ошибка в любую
  сторону искажает журнал — тестовая покупка в `live` даёт право без оплаты, настоящая в `test` не
  восстанавливается у игрока. Поэтому:
  - оба списка меняются одной операцией владельца, с записью в `WORK_QUEUE.md` (кто, когда);
  - пока список в кабинете не сверен с `OK_TEST_UIDS` (снимок кабинета), рабочий режим ОК не
    включается;
  - каждая запись журнала хранит, по какому правилу выбран режим (`by: 'uid-list'`), чтобы при
    обнаруженном расхождении записи можно было найти и разобрать вручную, а не угадать задним числом.

## 4. Проверка серверного восстановления без удаления прогресса

Нельзя проверять, стирая сохранение игрока или отключая облачные сохранения. **Сделано
(14 октября):** диагностическая сборка `npm run build:dachnye-tainy:oktest-diag -- --payments-url=<oktest>`
(`dist/ok-test-diag`). Вторая строка тестовой полосы показывает **ответ журнала `/ok/restore`
как есть**, независимо от того, что лежит в сохранении (облачном или локальном):
`журнал: без рекламы, подсказки` / `журнал: пусто` / `журнал: ошибка 403` / `ошибка сети` /
`нет ответа` / `неверный ответ`. Ни идентификаторов, ни подписи, ни адреса запроса на экране.
Сохранение и облако работают как обычно; права только добавляются.

Сценарии живой проверки:
1. Создатель с покупками → «журнал: без рекламы, подсказки». Это доказывает восстановление из
   журнала по подписанному `vk_ok_user_id` — **независимо** от того, что
   «Куплено» показывает и сохранение. Этот сценарий подтверждён владельцем.
2. Другой браузер → та же строка (журнал не зависит от браузера).
3. Второй аккаунт-тестировщик без покупок → «журнал: пусто» (журнал не выдаёт чужие покупки).
4. Сервер недоступен → «журнал: ошибка …», купленное в сохранении остаётся «Куплено».

Если журнал пуст при купленных товарах, проверить наличие подписанного `vk_ok_user_id`,
выбранный режим и адрес сервера. Одно пустое значение не устанавливает причину.

Временные пути `/ok/restore-token` и `/_diag/ledger` удалены после подтверждения
прямого подписанного восстановления. Токен API и сессия ОК для него не нужны.

Дополнительно, без изменения кода: DevTools → Network → запрос `…/ok/restore` → ответ
`{"skus":[…]}` (параметры запуска в адресе запроса не копировать — там подпись).

## 5. Архитектура рабочего режима: путь VK не трогаем

| Адрес | Сейчас | После перехода |
|---|---|---|
| URL уведомлений ВКонтакте | боевой Worker (код 22 сентября, без журнала) | тот же Worker + **только** правка `get_item` для `site=OK` (ветка `payments-prod-okprice`, снимок ответов VK побайтно) |
| URL уведомлений Одноклассников | `oktest` (тест) | **отдельный рабочий Worker ОК** (`dachnye-tainy-payments-ok`): журнал `LEDGER`, `PAYMENTS_MODE=live`, `OK_TEST_UIDS`; маршруты `/ok` и `/ok/restore` |

Почему отдельный Worker ОК, а не журнал в боевом: код основной ветки на пути VK строже версии
22 сентября (например, новый заказ без `item_price` отклоняется) — перенос его на боевой адрес VK
изменил бы VK-платежи. Отдельный Worker ОК не касается VK вовсе; VK получает только проверенную
снимком правку `get_item`.

Подготовлено локально:
- `selectOkMode`: тестировщик → `test`, остальные → `live` только с непустым
  корректным `OK_TEST_UIDS`, `OK_LIVE_ENABLED=1` и `OK_TEST_LIST_VERIFIED=1`;
  без любой из этих настроек рабочие платежи и восстановление заблокированы;
- запись `modeBy` в транзакции; повтор, найденный в другом режиме после изменения
  списка тестировщиков, блокируется для ручной сверки, а не переносится автоматически;
- отдельный `services/payments/wrangler.ok-live.toml`: оба переключателя выключены,
  личные ID и секреты не записаны. `OK_ONLY=1` закрывает маршруты VK;
- тесты разделения журналов, блокировок, восстановления и неизменности пути VK;
- локальная сборка Worker через `wrangler deploy --dry-run` прошла без развёртывания.

Следующий этап:
- настроить приватный список тестировщиков и секреты на отдельном сервере;
- до одобрения ОК проводить проверку на нём в `PAYMENTS_MODE=test`;
  включать `live` и оба переключателя только после отдельного подтверждения владельца
  о статусе модерации и повторной сверки списка. Одобрение VK не означает одобрение ОК;
- клиент: боевая сборка с `okPayments` и адресом рабочего Worker ОК — **только** для запуска в ОК;
  во ВКонтакте магазин и восстановление прежние.

(не планируется по умолчанию: перенос тестовых записей в рабочую базу смешивает режимы).
`oktest` и его журнал остаются для дальнейших тестов.
